# Cloudflare VPC 経由 VOICEVOX 実測メモ

計測日: 2026-08-30 (JST)

## 目的

絵描き歌の2候補を、歌詞選択前にどのように音声化するかを決めるため、通常経路である Cloudflare Worker からさくらの高専未来サーバー上の VOICEVOX へ、同じ歌唱スコアを同時送信した。

対象経路は次のとおり。

```text
計測端末
  → ローカル Wrangler Worker
  → Cloudflare VPC Service binding (remote)
  → Tunnel
  → VOICEVOX Engine :50021
```

公開Workerや本番D1を変更せず、ローカルD1にだけ短命の試験用 voice grant を登録した。合成リクエストは `backend: "vpc"` を明示し、Cloud Runへのフォールバックを無効にした。

## 計測条件

- VOICEVOX Engine: `0.25.2`
- VPC Service: `voicevox` / HTTP / `localhost:50021`
- 固定スコア: 28 notes / 1,322 frames
- 音声上の長さ: 約14.10秒 (`1322 / 93.75`)
- スコアSHA-256: `a7c8e9c2eb2786b615db7b80969193bae4885de6a52759f4ecbf30fcd0574902`
- 成功条件: HTTP 200、WAVのRIFF/WAVEヘッダー、`X-Voicevox-Backend: vpc`、`X-Voicevox-Fallback: false`

各並列度で、同じスコアと別々のワンタイムgrantを同時に送った。表の各時間は、リクエスト開始からWAV全体の受信完了までを示す。

## 結果

| 並列数 | 波 | 各リクエストの完了時間 | 波全体 | 成功 |
| ---: | ---: | --- | ---: | ---: |
| 1 | warm-up | 8.60秒 | 8.60秒 | 1/1 |
| 1 | 1 | 8.40秒 | 8.41秒 | 1/1 |
| 2 | 1 | 8.46秒、16.32秒 | 16.32秒 | 2/2 |
| 2 | 2 | 8.78秒、16.72秒 | 16.74秒 | 2/2 |
| 3 | 1 | 8.63秒、16.52秒、24.23秒 | 24.26秒 | 3/3 |
| 5 | 1 | 8.97秒、16.84秒、24.56秒、32.38秒、40.40秒 | 40.44秒 | 5/5 |

すべて676,908 bytesの有効なWAVで、HTTPエラー、VPC以外への到達、フォールバックはなかった。

## 判断

VOICEVOXは複数のHTTPリクエストを受理したが、この固定歌唱スコアでは約8秒間隔で1件ずつ完成した。現在のVPC先では、2候補を同時送信しても両方の完成は約16～17秒で、逐次送信より速くなる効果は見込めない。

この外形計測だけでは、VOICEVOXのCPUスレッド設定、CPU/RAM使用率、Engine内部の排他処理、Tunnel内の待ち時間は分離できない。ただし、少なくとも利用者から見た合成処理は実質的に1並列である。

5並列の最後は40.4秒で、Workerの歌唱クエリ制限45秒に近い。6件以上が同時に到達すると、サーバー自体が処理可能でも待機中のリクエストがタイムアウトする可能性が高い。

## 採用方針

1. A/B両候補を、メインの生成進捗が完了する前に再生可能な状態へする。
2. 同一利用者の2候補は並列送信せず、1件ずつ順番にVPCへ送る。サーバーへの突発的な待ち行列増加を避ける。
3. 両候補が「歌声あり」または「無音アニメーションのフォールバック」になった時点を生成完了とする。片方のVOICEVOX失敗で全体を失敗させない。
4. 歌詞選択後はキャッシュ済みの候補へ切り替え、通常フローでは追加合成を行わない。保存処理も音声合成を待たせない。
5. ローカルVOICEVOXとCloud Runの経路は維持するが、今回の性能判断には使用しない。
6. 複数端末を同時利用する展示では、まず同時利用台数を抑える。恒常的に6件以上の同時合成が必要になった段階で、Worker手前の明示的な全体キュー、タイムアウト、サーバー増強を別途設計する。

今回の結論は、1回の限定的な外形計測に基づく。サーバー設定変更後や本番前には、同じ固定スコアで複数波を再計測し、可能ならさくら側のCPU・RAM・load averageも同じ時刻で記録する。
