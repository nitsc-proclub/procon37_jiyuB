# 作品データの保存拡張メモ

更新日: 2026-09-01。**公開版へ導入済み。新しい同意を得た作品だけを保存する。**

## 2026-09-01 公開反映

- 非公開R2 `cho-ekaki-uta-creation-archives` とD1索引を接続した。`archives/` は365日後に削除するlifecycleを設定し、公開URLは無効のままにした。
- 新しい同意画面で、ブラウザ保存と、絵・線・A/B両候補・実音声・評価のクラウド保存を一度に確認する。拒否時は長期保存しない。
- 生成時に署名した画像・線・候補hashと評価receiptを保存APIで照合する。固定ファイル名、容量、MIME、JSON深さ、manifest、HMAC capabilityを検証する。
- D1の原子的な8 GB論理枠、pending/complete/deleting/deleted、アップロードlease、期限回収、R2孤児削除、削除レシートを実装した。削除時は紐づく評価・後続評価も削除する。
- 実ブラウザE2Eで、A/B合成、同意、7ファイルのアップロード、完了、保存管理画面を確認した。検証作品は1,401,347 bytesだった。

既存の評価・ブラウザ履歴を遡って収集しない。旧同意を新しい長期保存同意として扱わない。

## 方針

評価情報だけでなく、絵から歌ができるまでの素材も残す。改善・不具合調査・再現に役立つが、D1に画像や音声を詰め込まない。**明示的に同意した作品だけを、非公開R2へ保存する。D1は評価・検索・同意・ファイルの参照を担当する。**

既存の同意は「クラウドに絵・歌声・描いた線は送りません」という説明に対するもの。既存データ・ブラウザ履歴を遡って収集しない。新しい保存説明と同意versionを導入するまで、画像・音声の長期クラウド保存を有効にしない。

## 保存対象

| 対象 | 保存先・内容 |
| --- | --- |
| 入力の絵 | R2。生成に実際に使った画像1枚。PNGまたはロスレスWebP。base64ではなくバイナリ |
| 描いた線 | R2。座標・線順・色・太さ・stroke groupなど、再現に必要な構造化JSON |
| A/B両候補 | R2。表示歌詞、歌唱用読み、楽譜、同期マッピング、実際に得られた音声。未選択候補も保存 |
| 分析・評価 | 既存D1のDrawingAnalysis・2候補・選択・後続評価。大きい再現JSONはR2 |
| 再現情報 | R2 manifest。schema、アプリversion、モデルID、backend、生成パラメータ・時刻・欠損理由 |
| 同意・索引 | D1。generation ID、評価ID、同意version/時刻、用途、期限、ファイルkey/hash/bytes/MIME、状態 |

「すべて」は生成に使った作品素材と生成結果を指す。秘密鍵、grant/receiptの生値、認証ヘッダー、IP、氏名・年齢、端末全体の情報、無制限のデバッグログは含めない。写真などアプリに入力されていない情報も収集しない。音声が失敗して無音になった候補は、失敗・無音であることを記録し、音声を得るためだけに再合成しない。

学習への採用は保存同意とは別の審査段階。保存しただけで自動的に学習投入・公開配布しない。作品に個人情報が描かれる可能性があるため、管理者限定アクセスと削除手段を前提にする。

## 一時保存と長期保存を分離

| 用途 | 保存場所 | 期限・同意 |
| --- | --- | --- |
| 生成音声の受け渡し | 既存 `cho-ekaki-uta-voicevox-audio` の `wav/` | 初期論理TTLは作成から1時間、最大24時間以内。取得APIも期限を検査。lifecycle 1日は削除の安全網 |
| 同意済み作品の保管 | 専用の非公開R2 `cho-ekaki-uta-creation-archives` | 保管期限365日。同意時に説明し、期限後は削除。将来の延長は運用・説明を再検討 |

アプリを動かすための一時保持と、改善用の保管を混同しない。生成前の短い案内では「歌を届けるため、一時的に保存します」。保存を断った作品は長期保管へ移さない。ブラウザのローカル保存とクラウド保存の部分失敗も区別して通知する。

一時ファイルは取得直後に消さず、期限まで再取得できる形を第一候補にする。通信再試行・A/B再生・同意後の保管へのコピーがあるため。ただし、キャンセルや明示削除では期限前の削除も行う。長期bucketは一時bucketと分け、1日lifecycleによる誤削除を防ぐ。

## 容量の考え方

2026-08-31に公式資料を確認した。

- D1は1DB最大500 MB（Free）/10 GB（Paid）、1行・文字列・BLOBの上限2,000,000 bytes。画像やWAVの格納先にはしない。[公式制限](https://developers.cloudflare.com/d1/platform/limits/)
- R2 Standardは月10 GB-monthの無料枠、超過ストレージ$0.015/GB-month。Class A/B操作は別枠・別課金で、インターネット向け転送は無料。無料枠は他のR2利用と共有であり、このアプリ専用の容量ではない。[公式料金](https://developers.cloudflare.com/r2/pricing/)

以下は**実作品平均ではなく、設計用に1作品5 MBと仮定した試算**。A/B音声・絵・線・JSONの合計で、保持済み容量が1か月一定とする。GB/MBは十進単位。

参考として今回ローカル`demo-records/`を集計したところ、659件・合計約537.4 MB、1件平均815,466 bytes・中央値812,762 bytesだった。WAVは619件で平均747,508 bytes、PNG中央値27,861 bytes。これは主に1曲分の古い形式であり、A/B両方を保存する新形式の実測ではない。2曲化すればおおむね1.5 MB程度になる計算だが、余裕を見て容量設計は5 MB/作品とした。ファイル内容や作品画像はこのメモへ転記していない。

| 保管作品数 | R2容量の目安 | ストレージ月額の概算（他の利用なし） |
| --- | --- | --- |
| 1,000 | 5 GB | 無料枠内 |
| 10,000 | 50 GB | 約$0.60 |
| 100,000 | 500 GB | 約$7.35 |

操作回数、Workers/D1/Queue、税、料金単位の切り上げは別途。実際の月額は日ごとの保存量にも依存する。音声の測定例は14.1秒のWAVが676,908 bytes/曲で、2曲約1.35 MBだが、これは固定スコアであり、絵・線も含む実作品の平均を示さない。

索引だけを仮に10 KB/作品とすると10,000作品で約100 MB（index・既存評価JSON等は別）。D1も無制限ではない。実際の`bytes`合計・DB sizeを継続計測し、容量の80%で警告、90%で新規保管を停止する。停止しても生成・再生は止めない。

### 初期の安全上限（導入時に実装）

- 長期R2のアプリ論理予算をまず8 GBとする。無料枠を保証する値ではなく、蓄積を抑えるアプリ側の制限。他のR2利用と一時ファイル容量も監視する。
- 1作品は画像4 MiB、構造化JSON全体4 MiB、WAV各32 MiB、合計72 MiB以内。通常作品のサイズを測って後で縮める。JSONはさらに種類別の要素数・ネスト・文字数を制限する。
- アップロード前にD1で予約容量を原子的に確保し、同時保存で上限を超えないようにする。失敗予約の期限回収・孤児ファイルの削除まで実装する。
- 枠不足・サイズ超過では黙って画像や音声を捨てて「保存成功」にしない。「作品は保存できませんでした。歌は使えます。」とし、評価のみ成功した場合はその範囲も区別する。
- 容量確保のために同意済みの作品を無断で早期削除しない。期限削除と容量上限時の新規受付停止を基本にする。

## 同意文面案

> 絵と歌を保存してもいい？
>
> このブラウザで、あとから開けます。
> 絵・描いた線・2つの歌・答えを、アプリの改善のためクラウドに1年間保存します。
> 保存しなくても遊べます。

ボタンは「保存する」「保存しない」。保護者・指導者向けに、用途・非公開・削除方法・一時保持との違いを開ける短い詳細を用意する。名前などを書かない注意は入力画面の案内へまとめ、同意画面を長文にしない。スマホ縦・PC横で同じ内容にする。

## 実装順序と完了条件

現行のIndexedDB履歴/ZIPはアクティブ候補中心で、A/B両方を含む完全なsnapshotではない。既存receiptも分析と歌詞だけの署名で、画像・線・音声の整合性は保証しない。新保管APIでは画像/線の生成時hash、候補と音声の対応、同意versionを結び付ける契約が必要である。既存履歴上限は50件/100 MiBで、クラウド予算とは別管理にする。

1. 先にジョブの再送・lease fencing・短命R2受け渡しを実装/検証する。今回の次工程。
2. archive manifestとD1索引・容量予約・期限/削除状態を実装。大きいファイルは個別ストリーム転送し、base64一括JSONにしない。
3. receiptに結び付く生成ID・同意versionを検証した保管APIを追加。raw tokenや推測可能IDだけで取得・削除できないようにする。サーバーはclient申告のモデル/評価/任意R2 keyを信用しない。
4. 入力時点の画像・線と、A/B両方の結果を同一generationの不変snapshotとして保管。新しい歌への切替や候補選択で別作品が混ざらないようにする。
5. R2 upload→D1 completeを再試行可能にする。D1/R2は同一transactionではないためpending/complete/failed/deleting状態を管理。遅いuploadと削除・期限切れの競合も防ぐ。
6. 新同意UI、保管受付状況、削除手段を結線した後にfeature flagで公開。古い同意・拒否・枠不足・部分失敗・再送・キャンセル・期限切れ・旧generation完了を試験する。
7. 代表的な作品で実測し、件数/容量/単価を見直す。自動学習投入はこの工程に含めない。
